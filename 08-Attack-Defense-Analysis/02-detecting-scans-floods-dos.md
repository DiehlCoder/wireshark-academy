## 2. The TCP SYN Flood Attack

When a client sends a `TCP SYN`, the server allocates a data structure in kernel memory (the **TCP Backlog Queue**) and waits for the final `ACK`:

```
Normal 3-Way Handshake:
   Client ─── SYN ───► Server (Allocates socket buffer, State: SYN_RECV)
   Client ◄─ SYN/ACK ─ Server
   Client ─── ACK ───► Server (State: ESTABLISHED)

TCP SYN Flood:
   Attacker ─── SYN 1 (Spoofed IP) ───► Server (Allocates buffer, State: SYN_RECV)
   Attacker ─── SYN 2 (Spoofed IP) ───► Server (Allocates buffer, State: SYN_RECV)
   Attacker ─── SYN 3 (Spoofed IP) ───► Server (Allocates buffer, State: SYN_RECV)
   ... (Sends 100,000 SYNs; NEVER sends an ACK!)
   Server Backlog Queue Full! ──► Drops all legitimate user connection attempts!
```

### The Packet Signature in Wireshark:
1. Massive flood of packets matching: `tcp.flags.syn == 1 && tcp.flags.ack == 0`.
2. Extremely high ratio of SYN packets to SYN/ACK or ACK packets.
3. Randomized, spoofed source IP addresses or high-range source ports.
4. Window sizes and TCP options often identical across thousands of packets (generated by a tool rather than a real OS).

## 3. Application-Layer DoS: Slowloris

Unlike volumetric floods that blast gigabits of bandwidth, **Slowloris** operates at a whisper:
1. Opens 500 standard TCP connections to web server port 80.
2. Sends an incomplete HTTP request: `GET / HTTP/1.1\r\nHost: target\r\n`.
3. Periodically sends a bogus header byte every 15 seconds: `X-a: b\r\n`.
4. **Never sends the final CRLF CRLF (`\r\n\r\n`)!**
5. **Impact:** The web server (like Apache prefork) keeps 500 worker threads open waiting for the requests to finish. The server exhausts its `MaxRequestWorkers` limit and stops accepting new visitors, using less than **100 Kbps** of bandwidth!

## 4. 🎯 Mission: Simulate & Detect a SYN Flood with `hping3`

### Step 1: Start Wireshark on Kali
1. Launch Wireshark on `eth0`, filter: `tcp.dstport == 80`.
2. Open *Statistics ➔ I/O Graphs*:
   - Set interval to `0.1 sec` (100 ms).
   - Set Y-axis to `Packets/s`.

### Step 2: Launch a Controlled SYN Flood from Kali
On **Kali**, use `hping3` to generate a 5-second burst of SYN packets with randomized source IPs:
```bash
sudo hping3 -S --flood --rand-source -p 80 10.10.10.20
```
*(Allow it to run for **5 seconds**, then press `Ctrl + C` immediately!).*

### Step 3: Inspect Server State on Ubuntu Server
On **ubuntu-srv**:
```bash
# Check how many connections are trapped in SYN_RECV state:
ss -tn state syn-recv | wc -l
```

### Step 4: Dissect the Attack in Wireshark
1. In Wireshark, look at the I/O Graph:
   - Notice the massive vertical throughput wall spiking to tens of thousands of packets per second!
2. Inspect the packet list:
   - Notice thousands of SYN packets arriving from randomized public IP addresses (`198.51.100.42`, `203.0.113.89`...).
   - Look at the `Info` column: every packet is an initial `[SYN]`.
   - Filter `tcp.flags.syn == 1 && tcp.flags.ack == 1`: notice how Ubuntu Server desperately attempted to reply with SYN/ACKs to the fake spoofed IPs!

## 5. Defense: SYN Cookies & Cloud Scrubbing

### 5.1 SYN Cookies (RFC 4987)
Linux kernels include built-in protection called **SYN Cookies**:
- When the SYN backlog queue fills up, the server **stops allocating kernel memory** for half-open sockets.
- Instead, the server encodes the connection state into the **Initial Sequence Number (ISN)** of its `SYN/ACK` response using a cryptographic hash of the 5-tuple and a secret seed.
- When a legitimate client replies with `ACK`, the server reconstructs the state from the ACK number and opens the socket!

Verify SYN Cookies are active on Ubuntu Server:
```bash
sysctl net.ipv4.tcp_syncookies
# Output: net.ipv4.tcp_syncookies = 1 (Enabled!)
```

### 5.2 Cloud Scrubbing (Cloudflare, Akamai, AWS Shield)
Large volumetric DDoS attacks (often peaking at 500 Gbps to 2+ Tbps) easily overwhelm physical enterprise internet pipes.
Enterprises route their external traffic through global Anycast cloud scrubbing networks. Malicious botnet traffic is absorbed and filtered in the cloud, forwarding only clean, legitimate requests to the origin datacenter.

## 🧠 Knowledge Check
1. How does a TCP SYN flood exhaust server resources if the attacker sends zero bytes of payload?
2. What are **SYN Cookies**, and how do they defend against SYN flood attacks without dropping legitimate users?
3. How does a Slowloris attack take down a web server while using almost zero bandwidth?
4. What display filter isolates initial TCP SYN packets in Wireshark?

<details><summary>Answers</summary>

1. Each incoming SYN forces the operating system to allocate memory for a half-open socket entry in its TCP backlog queue. When the queue reaches its limit, the OS drops all subsequent connection attempts.
2. SYN Cookies eliminate the memory allocation during SYN receipt. The server encodes the connection state into the sequence number of the SYN/ACK packet and only allocates memory when a valid ACK is returned by a real client.
3. It opens hundreds of HTTP connections and sends partial headers slowly without terminating them, occupying all available web server worker processes so new requests cannot be handled.
4. `tcp.flags.syn == 1 && tcp.flags.ack == 0`.
</details>
